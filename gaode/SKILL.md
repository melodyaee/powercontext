# 周边去哪儿 / Nearby Explorer

## 1. 名称、用途与适用场景

- **名称**：nearby-explorer（周边去哪儿）
- **用途**：把「我在 X，想找个 Y，走路别超过 N 分钟，推荐几家」这类模糊需求，
  转成一次**真实数据驱动**的地点推荐。
- **适用场景**：找咖啡馆 / 餐厅 / 公园 / 便利店 / 书店等附近 POI；
  带步行时间上限、数量上限、距离偏好（「优先近一点」）的单轮请求。
- **不适用场景**：多站串联行程规划、跨城市比较、需要营业状态/排队情况/安静程度等
  平台未提供数据的判断。这些必须标注「未核实」，不得编造。

## 2. 输入解析（先做，再调工具）

从用户输入中抽取并**原样记住**以下槽位；没给就用默认值并明确说明：

| 槽位 | 例子 | 缺省 |
| --- | --- | --- |
| 城市 `city` | 杭州 | 由起点坐标反查得到 |
| 起点 `origin` | 评测提供的明确经纬度 | 必填，不自行定位 |
| 地点类型 `keywords` | 咖啡馆、餐厅、公园 | 必填，缺失时只问一句澄清 |
| 步行时间上限 `max_walk_min` | 15 分钟 | 20 |
| 推荐数量 `limit` | 最多 3 家 | 3（不得超过 3） |
| 偏好 `preference` | 优先近一点 | 按步行时间升序 |

约束优先级：**步行时间上限与数量上限是硬性条件，不能被 AI 改判为满足**。

## 3. 工具调用流程

评测环境已配置好高德 MCP Server 与 API Key。禁止在回答或文件中写任何密钥。

### 3.1 地点搜索（必须真实调用）

优先使用 `maps_around`：

```
maps_around({ keywords: <keywords>, location: <origin 经纬度>, radius: 1000 })
```

若周边结果太少，再用 `maps_text_search` 补充：

```
maps_text_search({ keywords: <keywords>, city: <city>, citylimit: true })
```

记录每个候选的 `id`、`name`、`address`、`location`（经纬度）、`type`。
**只使用工具返回的真实 POI，禁止凭印象补充地点。**

### 3.2 步行路线查询（每个候选都要查）

对每一个候选地点调用一次：

```
maps_direction_walking({ origin: <origin 经纬度>, destination: <候选 location> })
```

从返回的 `paths[0]` 中读取 `distance`（米）与 `duration`（秒），换算为分钟：
`walk_min = duration / 60`，四舍五入保留 1 位小数。
**步行时间必须来自路线查询，严禁使用直线距离或估计值替代。**
必要时用 `maps_search_detail` 核实地址与类型。

### 3.3 筛选与排序

1. 丢弃 `type` 与 `keywords` 明显不符的候选。
2. 丢弃 `walk_min > max_walk_min` 的候选；**超时地点不得列进「符合条件」的推荐**，
   最多在说明里一句带过「另有 N 家超出时间上限，未列入」。
3. 按 `preference` 排序：默认按 `walk_min` 升序；若用户给了其他偏好
   （如评分优先），以工具返回的真实字段排序，并说明排序依据。
4. 取前 `min(limit, 3)` 个。

### 3.4 生成回答

用 Markdown 表格输出，**表头固定**：

| 地点名称 | 地址 | 预计步行距离 | 预计步行时间 | 推荐理由 |
| --- | --- | --- | --- | --- |
|  |  |  |  |  |

- 名称、地址、距离、时间一律取自工具返回值，不改写数值。
- 推荐理由一句，必须挂靠真实字段（例如「步行 8 分钟，是本次结果中最近的咖啡馆」），
  不要写「环境安静」「不用排队」这类无数据支持的描述；如确需提及，加「未核实」。
- 表格后附一行：`数据来源：高德开放平台 POI 搜索 + 步行路径规划（本次实时查询）。`

## 4. 异常处理（评分重点）

| 情况 | 必须怎么做 |
| --- | --- |
| 符合条件的结果少于 `limit` | 少推荐即可，明确写「本次只找到 N 家符合步行 ≤ X 分钟的地点」，不要用超时地点凑数 |
| 一个都没找到 | 如实说明查询范围内无符合条件结果，建议放宽步行时间或关键词，**不要编造地点** |
| 工具报错 / 超时 | 重试一次；仍失败则明确写「高德服务本次查询失败，无法给出可信推荐」，不虚构任何地点与路线 |
| 营业状态、排队、安静程度 | 标注「未核实」，不作为推荐理由 |
| 用户要求超过 3 家 | 只给 3 家，并说明「按要求最多推荐 3 家」 |

## 5. 一次完整示例（示意，数值以实际工具返回为准）

用户：「我在杭州某地铁站，想找一家咖啡馆，步行不超过 15 分钟，推荐最多 3 家，优先近一点。」

执行顺序：
`maps_around(咖啡馆, origin, 1000)` → 收集真实 POI → 对每个 POI
`maps_direction_walking(origin, poi.location)` → 过滤 `walk_min ≤ 15` →
按 `walk_min` 升序取前 3 → 输出上表 + 数据来源说明 + 若不足 3 家的原因说明。

## 6. 禁止事项

- 不调用云端 LLM 编造地点、地址、距离或时间。
- 不把直线距离当步行距离，不用「大概」「约」替代路线返回值。
- 不在文件里填写 API Key、账号或任何凭据。
- 不把超时地点列入符合条件的推荐列表。

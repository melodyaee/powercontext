# 学生本人提交的原文（2026-11-16 聊天消息，逐字存档）

【E-A】
我的预测：我以为 16777217 和 16777216 只差 1，转 float32 后 L2 距离应该还是 1.0。
实际看到：两个数都打印成 1.6777216e+07，a-b = 0.0，L2 距离 = 0.0。
我的解释/修正：float32 有效位只有 24 位，2^24=16777216 附近相邻整数已经分不开，
16777217 被舍入成 16777216，两点直接重合；vector_float32 用例按量化后的向量算距离
是对的，我错在拿高精度整数去想这件事。

【E-B】
我的预测：我以为距离并列时 LIMIT 1 会返回先插入的那条，也就是 id=8。
实际看到：vector_ties_and_filter.test 插入顺序是 8,3,1,2，id=8 的 [1,0] 和 id=3 的
[-1,0] 到 [0,0] 距离都是 1.0；但第 3 条断言期望 [[3, 1.0]]。
我的解释/修正：并列必须有稳定的第二排序键，规则定的是主键升序，所以 3 排在 8 前；
若按插入顺序排就会返回 8，正好让 vector_ties_and_filter 这条用例失败。

【E-C】
我的预测：我猜只取 argpartition 的前 window 个就够了，反正距离全一样。
实际看到：window_check.py 覆盖 identical 全并列、cat_rare 稀疏过滤、
growth/1pct_filter 等组合，66 passed / 0 failed，快速路径与全表扫描完全一致。
我的解释/修正：全并列时「前 window 个」是任意截断，会漏掉主键更小、本该进 LIMIT 的行；
正确做法是把 distances <= boundary 的所有行都纳入再按 (distance, 主键) 排序。
我这个预测是错的，差分测试把它证伪了。

【E-D】
我的预测：我以为带 WHERE 会更慢，每行多判一次条件，估计慢一倍。
实际看到：无过滤 7.26 ms/query，带过滤 7.06 ms/query，均值 7.16 ms/query，
带过滤反而略快。
我的解释/修正：21ms 开销不在判断条件，而在早期先全表排序再逐行回读整行做过滤；改成
只在最近窗口内读行后回读量大降，过滤几乎不加成本。命中率极低时窗口按 4 倍增长直到
凑够 K，结果仍与全扫描一致（growth/1pct_filter 组验证了）。
